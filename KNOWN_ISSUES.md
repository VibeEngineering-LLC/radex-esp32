# Known Issues & Hardware Compatibility — radex-esp32

> **Для кого этот файл.** Это журнал известных проблем и их причин — он нужен, если что-то уже пошло не так, и написан подробно, для разбора. **Если у вас всё работает, читать его не нужно.** Инструкция по установке — [INSTALL.md](INSTALL.md), краткий обзор — [README.md](README.md).

Краткий справочник: какие платы мы реально проверили на Radex MR107ion BLE-шлюзе, какие проблемы клиенты ловят чаще всего, и что с этим делать. Длинные технические разборы инцидентов с прошлой разработки — в [README.md](README.md), раздел «Стабильность платформ».

## 1. Матрица совместимости плат (hardware compatibility)

> **Дисклеймер.** Работа подтверждена только на платах со статусом ✅. Для всех остальных — **гарантий нет**. Если попробовал и получилось/не получилось — открой [issue](https://github.com/VibeEngineering-LLC/radex-esp32/issues), добавим в матрицу.

> **Матрица относится к ветке ESPHome** (`firmware/*.yaml`, релизы v0.1.0 – v0.5.0). Ветка ESP-IDF (`firmware-idf/`, релиз v1.0.0) имеет собственные, более узкие требования к железу — они в подразделе 1.1 ниже, и переносить на неё строки этой матрицы нельзя.

### ✅ Протестированы и рекомендованы

| Плата | Чип | Flash | PSRAM | Антенна | YAML | Заметки |
|---|---|---|---|---|---|---|
| **ESP32-S3-DevKitC-1 N16R8** ⭐ | ESP32-S3 dual-core 240 MHz | 16 MB | 8 MB embedded octal | PCB + **U.FL/IPEX** | `firmware/radex_gateway_s3.yaml` (arduino) | **Рекомендованная плата.** Стабильна на arduino, PSRAM позволяет держать Web UI с `log: true`, U.FL для внешней антенны. USB-C. На smoke-тест новой платы — `firmware/radex_gateway_s3_baseline.yaml`. |
| **ESP32-DevKitC v4 (WROOM-32 / WROVER)** | ESP32 classic dual-core 240 MHz | 4 MB | — | PCB | `firmware/radex_gateway.yaml` (esp-idf v0.3.0-step8) или `firmware/radex_gateway_v2.yaml` (Web UI v2) | ⚠ Работает в **узкой конфигурации**: esp-idf + `web_server.log: false` + `bluetooth_proxy: # active: true` (закомментирован). Любая попытка вернуть `log: true` или включить bt-proxy → `json:111`, OOM. |

### ❌ НЕ работает / не подходит

|---|---|

| **ESP32-S2** | Нет BLE — физически не может быть BLE-шлюзом к Radex. |
| **ESP8266 (любой)** | Нет BLE. |

### ⚠ Не протестированы — на свой риск

| Плата | Ожидание |
|---|---|
| **XIAO ESP32-C3** (Seeed) | Для Radex не пробовали. NimBLE BLE 5.0 есть, но потребуется отдельный YAML — текущие наши под C3 не пойдут (см. INC-C3-001). |
| **ESP32-C6 / H2** | BLE 5.0 LE поддерживается, NimBLE OK, но YAML под них в скилле не написан. |
| **ESP32-S3-DevKitC-1 N8R2 / N4R2** | Меньше Flash/PSRAM. `radex_gateway_s3.yaml` ориентирован на N16R8; на меньших ревизиях нужно править `flash_size`, `partition` и `psram: mode`. |
| **«Голый» ESP32-S3 без PSRAM или с QSPI PSRAM** | Меняй `psram.mode: octal` → `quad` или убирай блок целиком; `web_server.log: false` без переспроса. Лучше взять оригинальную N16R8 от Espressif. |

### 1.1. Ветка ESP-IDF (`firmware-idf/`, релиз v1.0.0)

Отдельная реализация шлюза на C, не наследующая ограничения ESPHome-конфигураций и не наследующая их совместимость. Требования заданы в [`firmware-idf/sdkconfig.defaults`](firmware-idf/sdkconfig.defaults) и [`firmware-idf/partitions.csv`](firmware-idf/partitions.csv):

| Требование | Значение | Откуда |
|---|---|---|
| Чип | **ESP32-S3** | `CONFIG_IDF_TARGET="esp32s3"` |
| Flash | **16 МБ** | `CONFIG_ESPTOOLPY_FLASHSIZE_16MB=y`; таблица разделов занимает до `0x820000` (два слота OTA по 3 МБ + 2 МБ под историю) |
| PSRAM | **обязательна, octal** | `CONFIG_SPIRAM_MODE_OCT=y`; кольцевой буфер лога берёт из неё 384 КБ, размещения в оперативной памяти для него не написано |
| Bluetooth | Bluedroid, BLE 4.2, **BLE 5.0 выключен** | `CONFIG_BT_BLE_50_FEATURES_SUPPORTED=n` — см. `INC-BLE50-001` |

Проверено: **ESP32-S3-DevKitC-1 N16R8** — прогон 36 ч 54 мин, 884 цикла опроса, 0 ошибок чтения (измерение приведено в `INC-BLE50-001`). Другие платы под этой веткой не проверялись; на S3 с меньшим флешем либо с quad-PSRAM образ из релиза не заработает, а сборка потребует правки `sdkconfig.defaults` и `partitions.csv`. Скрипт сборки принимает цель `esp32c3` через переменную `RADEX_TARGET`, но результат на C3 не проверялся и в матрицу не входит.

Известные ограничения самой ветки, не связанные с платой:

- **Веб-интерфейс без аутентификации** — страница и все маршруты `/api/*`, включая перезагрузку и изменение настроек, доступны любому в той же сети. В ESPHome-ветке этот интерфейс закрыт Basic Auth.
- **Пароль Wi-Fi хранится в NVS открытым текстом** (`main/wifi_manager.c`) — вычитывается из флеша при физическом доступе к плате. Шифрование флеша выключено по умолчанию: оно включается необратимо, прожигом eFuse.
- **Полевой режим (точка `RadexGW-Outdoor`) снимается только стиранием флеша** — средства выключить его из веб-интерфейса в версии 1.0.0 нет.
- **Прежний `sdkconfig` перекрывает `sdkconfig.defaults`** — после смены цели или фичесета его нужно удалить, иначе собранный образ не соответствует конфигурации в репозитории.

## 2. Рекомендации по выбору железа

1. **Покупаешь новую плату под продакшен**: **ESP32-S3-DevKitC-1 N16R8** (Espressif оригинал). Стабильна, есть запас по памяти под Web UI v3 + sliding-window средние, U.FL для внешней BLE-антенны, USB-C. Прошивка — `firmware/radex_gateway_s3.yaml`, smoke-тест — `firmware/radex_gateway_s3_baseline.yaml`.
2. **Уже есть классический ESP32-DevKitC v4**: используй `firmware/radex_gateway.yaml` (esp-idf, v0.3.0-step8, `log: false`, bt-proxy закомментирован) или `firmware/radex_gateway_v2.yaml` (Web UI v2). Любое отклонение от этой конфигурации (включить лог, вернуть bt-proxy) → json:111.
3. **Ставишь ветку ESP-IDF** (релиз v1.0.0): выбора нет — **ESP32-S3-DevKitC-1 N16R8**, требования в подразделе 1.1. Та же плата подходит и для ESPHome-ветки, так что при сомнении в выборе ветки она оставляет открытыми оба пути.
4. **Что не брать**:
   - ESP32-C3 SuperMini (плохая PCB-антенна у части партий + готового YAML нет).
   - ESP32-S2 / ESP8266 (нет BLE).
   - Безымянные клоны S3 без PSRAM или с QSPI PSRAM (поломанный baseline).

## 3. Инциденты

### INC-C3-001 — `OSError: [Errno 28] No space left on device` при прошивке ESP32-C3 SuperMini

- **Дата:** 2026-06-19
- **Скилл:** radex-esp32 (симптом идентичен в atomfast-esp32)
- **Severity:** блокирует прошивку

**Симптом.** При попытке `esphome run --device COMx radex_gateway_s3.yaml` (или другой YAML с разметкой на 16 MB Flash) на плату **ESP32-C3 SuperMini** в логе появляется:

```
OSError: [Errno 28] No space left on device
```

Текст звучит как «кончилось место на диске PC», но на host-машине места много (десятки/сотни GB свободно). Ошибка приходит из esptool / arduino-builder / esp-idf flash tool.

**Корень.**

1. `radex_gateway_s3.yaml` рассчитан на **ESP32-S3-DevKitC-1 N16R8** — Flash 16 MB. Параметры `esp32.flash_size` и таблица партиций в YAML соответствуют 16 MB.
2. **ESP32-C3 SuperMini** имеет **4 MB Flash**.
3. При записи esptool проверяет `partition_table.end_offset > chip_flash_size` → `ENOSPC` (`Errno 28`).

Дополнительные факторы:
- `radex_gateway.yaml` / `radex_gateway_v2.yaml` (классический DevKitC) тоже не подойдут для C3 — они под `board: esp32dev` и **Bluedroid** BLE-стек, а C3 поддерживает **только NimBLE**. Компиляция упадёт ещё до flash на этапе линковки.
- Web UI v3 с sliding-window средними hour/day + 4-handle round-robin BLE poll на 400 KB SRAM C3 (без PSRAM) — даже если соберётся, рискует OOM на F5.

**Решение.**

- **Не пытаться прошить существующие YAML на ESP32-C3** — ни `_s3.yaml`, ни классику. Они не для C3.
- Для Radex→HA шлюза на C3 нужен **отдельный YAML** под `board: esp32-c3-devkitm-1`, `framework: arduino`, partition `min_spiffs.csv`, NimBLE-стек, упрощённый Web UI без `log: true`. На момент 2026-06-19 такого YAML в репо нет.
- **Рабочая альтернатива:** перейти на **ESP32-S3-DevKitC-1 N16R8** и использовать готовый `radex_gateway_s3.yaml`.

**Профилактика.** Перед прошивкой незнакомой платы проверь физический Flash:

```bash
esptool.py --chip esp32c3 --port COM3 flash_id
# покажет MAC, chip rev, и Detected flash size: 4MB
```

Параметр `esp32.flash_size` в YAML должен совпадать с этим значением. Несовпадение → ENOSPC при записи.

### INC-FW18-001 — данные не идут: соединение рвётся через 5–12 с (ИСПРАВЛЕНО)

**Симптом.** Плата подключается к прибору, но данные не идут: в Web UI `успешных
коннектов = 0`, в логе цикл «подключились → разрыв через 5–12 с» с кодом `reason = 8`.
Прибор при этом штатно работает с телефоном и с ПК.

**Причина.** Дефект на стороне шлюза, не прибора. Bluedroid по умолчанию сам запускает
service discovery на каждом соединении (`auto_disc = TRUE`, `bta_gattc_act.c`) —
независимо от кода приложения. На MR107ion этот автоматический discovery не завершается,
и наши ATT-чтения встают в очередь позади него: соединение живёт несколько секунд и
умирает, не отдав ни байта. Симптом выглядит как «прибор не отвечает», хотя прибор
исправен и запросов от нас попросту не получает.

**Решение.** Отключить авто-discovery вызовом `BTA_GATTC_AutoDiscoverEnable(0)`, причём
ТОЛЬКО из обработчика `ESP_GATTC_REG_EVT`: вызов из `app_main()` затирается поздним
сбросом флага внутри `bta_gattc_enable()`. Реализовано в
[`firmware/include/radex_read_hook.h`](firmware/include/radex_read_hook.h).

**Измерено на ESP32-S3:** без вызова — разрывы каждые 5–12 с и 0 успешных чтений;
с вызовом — 705 чтений и 0 разрывов за 900 с.

**Сопутствующее требование (в силе).** Прибор не обслуживает ничего, пока не получит
ответ на свой `Exchange MTU Request`, — центральному нужен включённый GATT-сервер.
В ESPHome это компонент `esp32_ble_server:` либо
`sdkconfig_options: CONFIG_BT_GATTS_ENABLE: y`.


### INC-BLE50-001 — связь не восстанавливается после разрыва: `Cmd Disallowed` на opcode 0x2043 (ИСПРАВЛЕНО)

**Симптом.** Первое подключение к прибору проходит штатно (`MTU=64`, показания идут), но
после любого разрыва связи каждая последующая попытка переподключения отклоняется
контроллером:

```
W BT_L2CAP: is_aux auto-set to true (BLE 5.0 API used)
W BT_HCI:   opcode=0x2043, status= 0c: Cmd Disallowed
W BT_APPL:  gattc_conn_cb: if=4 st=0 id=4 rsn=0x100
```

Интервал повторов растёт до потолка и остаётся там неограниченно долго; связь не
восстанавливается ни сама, ни по истечении часов. Единственным известным лечением до
разбора оставалось полное снятие питания платы — программные средства уровня приложения
результата не давали.

**Причина.** Конфигурационная, не аппаратная. В собранном `sdkconfig` одновременно
оказались включены два взаимоисключающих набора возможностей:

```
CONFIG_BT_BLE_42_FEATURES_SUPPORTED=y
CONFIG_BT_BLE_50_FEATURES_SUPPORTED=y
```

Документация Espressif (`components/bt/host/bluedroid/Kconfig.in`) прямо указывает, что
BLE 4.2 и BLE 5.0 не могут использоваться одновременно. Проект включал 4.2 осознанно —
ради `esp_ble_gattc_open()`; набор 5.0 приходил значением по умолчанию и не отключался.

Последствие сочетания прослеживается по исходникам Bluedroid. Функция
`esp_ble_gattc_open()` (`api/esp_gattc_api.c`) явно выставляет `is_aux = false`, то есть
запрашивает legacy-соединение, однако `stack/l2cap/l2c_ble.c` переопределяет запрос на
extended-соединение (HCI opcode `0x2043`) через флаг, который после установки не
сбрасывается. После разрыва с `reason = 8` контроллер (закрытый бинарный компонент,
исходников не имеет) перестаёт принимать эту команду и отвечает `Cmd Disallowed` на все
последующие попытки.

Дефект того же класса на других чипах описан в
[esphome/esphome#18047](https://github.com/esphome/esphome/pull/18047) — одновременное
включение обоих наборов приводило к аналогичному отказу переподключения.

**Решение.** Явно отключить набор BLE 5.0 в `sdkconfig.defaults`:

```
CONFIG_BT_BLE_50_FEATURES_SUPPORTED=n
```

Проверка применения — по собранному образу, не по конфигурационному файлу: в логе старта
контроллер сообщает `BLE_INIT: Feature Config, ADV:1, BLE_50:0, …`, а символ
`btsnd_hcic_ble_ext_create_conn` в карте линковки отсутствует (используется
`btsnd_hcic_ble_create_ll_conn`, legacy opcode `0x200D`).

Ранее существующий `sdkconfig` необходимо удалить перед пересборкой — он перекрывает
значения из `sdkconfig.defaults`.

**Измерено на ESP32-S3 (ESP-IDF 6.1).** Непрерывный прогон 36 ч 54 мин без перезагрузок:
884 успешных цикла опроса, 0 ошибок чтения, 1 разрыв связи. Единственный разрыв
восстановлен автоматически с первой попытки — счётчик неудачных открытий соединения не
увеличился, `Cmd Disallowed` за весь прогон не появилось ни разу. До исправления тот же
класс отказа приводил к безвозвратной потере связи.

**Дополнительная мера (не заменяет исправление).** Введён счётчик подряд неудачных
попыток открытия соединения; при достижении порога выполняется программный перезапуск
`esp_restart()`. Возможность такого восстановления подтверждена отдельно: ручной
программный перезапуск на зависшей плате снимал отказ полностью, то есть снятие питания
не является обязательным. За 37 часов прогона после исправления конфигурации механизм не
потребовался ни разу и остаётся резервным.

## 4. Частые ошибки установки клиентов

См. [INSTALL.md](INSTALL.md), раздел **Troubleshooting** — там пошаговый разбор 10+ типовых проблем (драйвер CH340/CP210x, COM5 = SoundBlaster, `UnicodeDecodeError` с кириллицей в пути, BOOT-handshake, `Auth Expired`, OTA после смены пароля, `json:111`, `Invalid key format` для `api_encryption_key`).

**Самая частая (≈30 % обращений):** `Invalid key format, please check it's using base64.` на этапе `esphome compile`. Лечится одной командой:

```bash
python -c "import secrets,base64; print(base64.b64encode(secrets.token_bytes(32)).decode())"
```

Полученную 44-символьную base64-строку положить в `secrets.yaml` как `api_encryption_key:`, заменив весь placeholder. Та же команда работает и для `ota_password` (или короче — `openssl rand -base64 32`).
