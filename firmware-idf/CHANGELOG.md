# Changelog — ветка ESP-IDF (`firmware-idf/`)

Версионирование: semver, номер совпадает с тегом релиза на GitHub. Дата — UTC+3.
Изменения ветки ESPHome ведутся отдельно, в [`../firmware/CHANGELOG.md`](../firmware/CHANGELOG.md).
Версии до v1.13.0 описаны в текстах релизов на GitHub:
<https://github.com/VibeEngineering-LLC/radex-esp32/releases>.

## v1.13.1 (2026-09-19) — установка часов прибора по USB выключена по умолчанию; исправлена колонка oa журнала по USB

### Исправлено

- **Колонка `oa` журнала по USB — скользящее среднее (как по BLE); прежняя сборка v1.13.0 отдавала
  сырую ОА.** BLE-запись журнала (24 байта) — это USB-запись (22 байта) со сдвигом на 2 байта, поэтому
  `oa` (то, что рисуют таблица журнала и «Сохранить в историю») в BLE-записи — скользящее среднее
  (USB @12, его показывает экран прибора), а `unk_f10` — сырая ОА цикла (USB @8); шлюз v1.13.0 клал их
  наоборот, и журнал по USB давал другую кривую, чем по BLE. Теперь соответствие полей — в одной
  функции `radex_arch_to_journal()` (`main/radex_ekosf.c`): `oa` = скользящее, `unk_f10` = сырая,
  `raw2` = индекс сессии, `seq` = номер−1. Сверено: USB-запись №3 из трассы RadexDC совпадает с
  записью №3 из BLE-захвата (тот же образец `REC3` в `test_journal_parse.c`) во всех полях;
  на плате запись №264 сессии 0 по BLE — `oa` 79,31 (скользящее), сырая по трассе 97,33.
  Хост-тест `test_radex_sessions.c` сравнивает USB-запись с BLE-разбором побайтно (1:1) и проверен
  мутационно (возврат прежнего присваивания краснит тест).
  Поля `summary` (`avg`, `sko`, `raw2`, `raw4`, `last_record`) сверены по раскладке (тот же сдвиг
  на 2 байта) и соответствуют BLE-разбору; живые сводки BLE и USB побайтно не сравнивались.

### Изменено

- `CONFIG_RADEX_USB_CLOCK_SYNC` по умолчанию **n** (`main/Kconfig.projbuild` и явно в
  `sdkconfig.defaults`). Причина: по наблюдению за RadexDC установка времени (`0x0006`)
  закрывает текущую сессию замера на приборе и открывает новую, а с платы она не проверялась.
  При выключенной опции код синхронизации не компилируется; запрос `0x0006` остаётся в белом
  списке (`radex_ekosf.c`), но не вызывается. Включить — `CONFIG_RADEX_USB_CLOCK_SYNC=y`
  (порог расхождения — `CONFIG_RADEX_USB_CLOCK_MAX_DRIFT_S`) и пересборка; переключателя без
  пересборки нет.
- `firmware-idf/version.txt` — `v1.13.1` (поле `fw` в `/api/system`).

### Документация

- Заголовки README («Альтернативная архитектура: чистый ESP-IDF») и INSTALL («Путь 3: ветка
  ESP-IDF») больше не привязаны к версии; исправлены битые якоря на них.

### Известное поведение (не исправлялось)

- Журнал по BLE читает только сессию 0: при двух сессиях на приборе `/api/journal` по BLE отдаёт
  старую сессию (`last_record` 264), по USB — последние 64 записи сквозь сессии. Это поведение BLE-кода
  v1.12.0; наблюдалось на плате 19.09.

Остальное — как в v1.13.0. Исходники прошивки, кроме описанного выше, не менялись.

## v1.13.0 (2026-09-18) — прибор по USB-кабелю, автовыбор USB/BLE

### Добавлено

- **Канал USB.** Плата ESP32-S3 работает USB-хостом, MR107ion подключается к разъёму OTG как
  устройство CDC-ACM (`ABBA:A204`, 230400 8N1; DTR=0 первой командой после открытия, RTS=1).
  Протокол EKOSF/RPC разобран по трассам USB обмена штатной программы с прибором:
  - текущие показания — RPC `0x0BC2` (ОА последнего цикла, средняя сессии и её СКО,
    скользящее среднее, температура, влажность, часы прибора);
  - журнал — `0x0C04` → `0x0C0D` → `0x0C05` → страницы `0x0C0E` по 22 записи, последние
    64 записи через границу сессий прибора; с паузой после `0x0C05`, как у штатной
    программы (без неё прибор отдаёт страницу с прежней позиции);
  - часы прибора — RPC `0x0006` по времени платы: только после NTP, при расхождении > 5 с,
    не чаще раза в 6 ч. **ВНИМАНИЕ:** по наблюдению за RadexDC установка времени закрывает
    текущую сессию прибора и открывает новую (сбрасывает «среднюю сессии»); на плате `0x0006`
    не проверялась. Отключается сборкой: `CONFIG_RADEX_USB_CLOCK_SYNC=n` (в v1.13.0 была включена
    по умолчанию; с v1.13.1 выключена).
  Прибору уходит только белый список из шести запросов (`main/radex_ekosf.c`,
  `radex_req_allowed()`): три чтения (`0x0BC2`, `0x0C0D`, `0x0C0E`), два позиционирования архива
  (`0x0C04`, `0x0C05`) и одна запись — установка часов (`0x0006`). Все прочие RPC отклоняются
  до отправки.
- **Автовыбор канала** (`main/radex_link.c`): прибор на USB → USB, BLE на паузе; USB нет
  10 с → BLE как в v1.12.0; переходы на лету, без перезагрузки.
- **Выключатель Bluetooth** — флажок в карточке «Прибор (MAC)», `POST /api/bt`, поле
  `bt_enabled` в `/api/system`; хранится в NVS, по умолчанию включён.
- `transport` (`usb` | `ble` | `none`) в `/api/data`; приставка «USB · » / «BLE · » к строке
  статуса опроса.
- Внутренняя память в `/api/system`: `int_free`, `int_min`, `int_largest`, `dma_free`.
- Хост-тесты `test_radex_ekosf.c`, `test_radex_sessions.c` на кадрах из трасс (векторы
  `test/host/radex_usb_vectors.txt` извлекаются скриптом, руками не набираются).

### Изменено

- Буферы Wi-Fi и lwIP — в PSRAM (`CONFIG_SPIRAM_TRY_ALLOCATE_WIFI_LWIP=y` с профилем Wi-Fi,
  явно в `sdkconfig.defaults`). Без этого образ USB+BLE оставлял ~1 КБ внутренней памяти, и
  страница не отдавалась (KNOWN_ISSUES, `INC-USB-MEM-001`).
- `ble_radex_start()` возвращает управление: BLE живёт в своей задаче.
- Счётчики чтений/ошибок/разрывов/неудачных подключений в `/api/data` — сумма по обоим
  каналам.
- Мощность BLE в `/api/system` запрашивается у контроллера, только если стек BLE поднят
  (иначе `ble_tx_dbm` = 0).

### Совместимость

HTTP API и формат JSON — прежние; новые поля только добавлены. Таблица разделов не менялась:
настроенную плату обновлять приложением на `0x20000`.

### Известные ограничения и не проверено на плате

- Установка часов прибора с платы (`0x0006`) на живом приборе не проверялась; синхронизация
  включена по умолчанию и может начать новую сессию на приборе (см. выше).
- Чтение журнала по BLE в универсальной сборке не проверялось (код BLE-журнала не менялся).
- Включение Bluetooth флажком на странице не проверялось (выключение — проверено;
  включение через `POST /api/bt` — проверено).
- Смещения @74/@76 ответа `0x0BC2` (число сессий, текущая сессия) подтверждены на двух
  трассах; при трёх и более сессиях не проверялись.
- Во время работы USB-хоста вторичная консоль USB-Serial-JTAG недоступна; лог — через UART.
