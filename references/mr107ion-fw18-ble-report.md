# Radex MR107ion с прошивкой 1.8: прибор не обслуживает GATT-запросы, если центральное устройство — ESP32

**Технический отчёт для специалиста по BLE / изготовителя прибора**
Дата: 2026-08-27 · Проект [radex-esp32](https://github.com/VibeEngineering-LLC/radex-esp32) · Связанный тикет: [issue #1](https://github.com/VibeEngineering-LLC/radex-esp32/issues/1)

---

## 1. Резюме

Радон-детектор **Quarta-Rad Radex MR107ion, прошивка прибора v1.8** (Device Information Service: `fw_revision = v1.8`, `sw_revision = 840`, LMP-производитель Nordic Semiconductor) **не отвечает ни на один ATT-запрос**, если центральным устройством выступает **ESP32/ESP32-S3**. Тот же экземпляр прибора без единой ошибки работает с Windows (25 часов непрерывного чтения) и с Android (полный discovery за 14 мс).

Наблюдаемая со стороны ESP32 картина воспроизводится в 100 % попыток:

1. Соединение на канальном уровне устанавливается штатно.
2. Прибор **сам** инициирует `Exchange MTU Request` (Client Rx MTU = 64), получает ответ — и на этом обмен заканчивается.
3. На `Read By Group Type Request` (начало service discovery) и на любой последующий ATT-запрос прибор **не отвечает никогда** — `SEARCH_RES`/`SEARCH_CMPL` не приходят ни разу за всю серию опытов.
4. Через 5–9 секунд линк рвётся по `reason = 0x08` (HCI Connection Timeout), то есть прибор перестаёт отвечать и на канальном уровне.

**Что уже исключено измерением:** железо шлюза (две разные платы), хост-стек (Bluedroid и NimBLE ведут себя одинаково), работоспособность нашего клиента (против эталонного `gatt_server` из ESP-IDF discovery проходит и линк живёт), конфигурация соединения (интервалы, supervision timeout, MTU, шифрование, DLE, PHY, приватность адреса — по отдельности и в полной имитации телефона).

**Что осталось:** различие лежит на уровне Link Layer / контроллера ESP32 по отношению к Link Layer прибора. Для локализации нужен либо внешний сниффер эфира, либо взгляд со стороны изготовителя на то, при каком условии BLE-стек прибора v1.8 перестаёт обслуживать ATT.

**Указание на регрессию:** экземпляр того же прибора с **прошивкой 1.7** работает с тем же ESP32-шлюзом штатно — 19 часов аптайма, 0 реконнектов, данные текут. Это единственное известное нам различие между работающей и неработающей связкой.

```
247   1,479   Sent Read By Group Type Request, Primary Service   <<< начало discovery

 …             discovery проходит полностью: GAP, GATT, NUS, DIS, fe6516xx, fe6517xx
678   8,146   Sent LE Set Data Length (ЯВНЫЙ запрос телефона): TxOctets 64
682   8,313   LE Data Length Change — Max TX Octets 64
```

### 4.2 Четыре факта, видимые только из этой трассы

1. **Прибор всегда первым шлёт `Exchange MTU Request` и не обслуживает ничего до ответа на него.** Для нас это оказалось критично (§6.1).
2. **DLE у телефона стоит на минимуме (27 октетов) всё время discovery** и расширяется до 64 только через 7,1 с — уже после того, как всё перечислено. У ESP32 контроллер инициирует DLE сам на +260 мс, то есть **до** discovery.
3. **PHY Update не выполняется вообще** — проверено по всему логу (`bthci_cmd.opcode == 0x2032/0x2031`, `le_meta_subevent == 0x0c` → 0 кадров). Телефон всю сессию на 1M PHY; прибор 2M и не объявляет.
4. **Шифрования нет ни одного кадра** — SMP не запускается, прибор не требует сопряжения.

Отдельно проверено: в окне кадров 153–246 **нет ни одного ATT-кадра от прибора**. К GATT-серверу телефона прибор не обращается — сервер нужен ему исключительно как адресат `Exchange MTU Request`.

## 5. Поведение ESP32 — что именно наблюдается

### 5.1 Типичный цикл (воспроизводится всегда)

```
I (3799) radex_idf: GATTS MTU_EVT mtu=64        <-- прибор спросил, мы ответили
I (3819) radex_idf: GATTC OPEN_EVT status=0     <-- линк открыт
I (3830) radex_idf: DISCOVERY ret=0             <-- отправлен Read By Group Type Request
        … тишина: ни SEARCH_RES, ни SEARCH_CMPL …
I (11100) radex_idf: DISCONNECT reason=8        <-- HCI Connection Timeout, через 5–9 с
```

То же самое на NimBLE:

```
mtu update event; mtu=64
Connection established
Error: Service discovery failed; status=7      = BLE_HS_ENOTCONN
disconnect; reason=520                          = 0x200 + HCI 0x08 (Connection Timeout)
```

### 5.2 Порядок событий, который стоит знать интегратору

`ESP_GATTS_MTU_EVT` приходит **раньше** `ESP_GATTC_OPEN_EVT` (3799 мс против 3819 мс). Состояние обмена MTU нельзя сбрасывать в `OPEN_EVT` — это затирает уже состоявшийся обмен.

### 5.3 Разрыв — это молчание прибора, а не наш таймер

Проверено управляемой переменной: при изменении supervision timeout «время жизни» соединения меняется пропорционально.

| Заданный supervision timeout | Наблюдаемое «прожило» |
|---|---|
| 3200 (32 с) | 34,7 / 37,9 / 41,0 с |
| 400 (4 с) | 4,1 / 6,1 / 7,0 / 6,5 / 6,6 / 4,9 с |

Разрыв всегда `reason = 8`. Уменьшение таймаута в 8 раз даёт падение «удержания» в 6–8 раз. Поскольку supervision timeout отсчитывается от последнего принятого пакета, это означает: **прибор замолкает на канальном уровне в первые секунды после подключения**, а всё, что раньше принималось за длительность связи, — длина нашего собственного таймера.

## 6. Что проверено и чем закончилось

### 6.1 Единственная найденная настоящая ошибка на нашей стороне

**`CONFIG_BT_GATTS_ENABLE=n`.** В первой версии прошивки GATT-сервер был выключен как ненужный — шлюз только читает прибор. Из-за этого Bluedroid физически не имел чем ответить на `Exchange MTU Request`, который прибор шлёт первым. После `CONFIG_BT_GATTS_ENABLE=y` + `esp_ble_gatts_app_register()` с пустым обработчиком прибор впервые получил ответ: `GATTS MTU_EVT mtu=64` проходит теперь в каждом цикле.

**Для пользователей ESPHome:** это включается компонентом `esp32_ble_server:` либо явно через `sdkconfig_options: CONFIG_BT_GATTS_ENABLE: y`.

Однако **исправление необходимо, но не достаточно** — после него прибор отвечает ровно на одно и продолжает игнорировать discovery.

### 6.2 Сводка прогонов автоматической петли (2026-08-26)

Каждый прогон: сборка → прошивка → 90–120 с захвата с UART → разбор сырого лога тремя независимыми путями (grep-метрики, локальная модель-разборщик, слепой проверщик).

| # | Конфигурация | Циклов | `SEARCH_CMPL` | Удержание, с | Код разрыва |
|---|---|---|---|---|---|
| 1 | baseline (только GATTS-фикс) | 4 | **0** | ~7 | 0x8 |
| 2 | DLE cap 27 октетов | 4 | **0** | 6,5–8,4 | 0x8 |
| 3 | DLE cap 64 октета | 5 | **0** | 6,7–9,1; один 38,4 | 0x8, один 0x3E |
| 5 | PHY 1M only | 3 | **0** | 6,9 / 8,9 / 14,0 | 0x8 |
| 6 | DLE 27 + PHY 1M | 3 | **0** | до **42,3** (максимум серии) | 0x8, один 0x100 |
| 10 | полная имитация телефона (DLE 27 + PHY 1M + явный conn update 7,5 мс) | 6 | **0** | 5,0–8,3 | 0x8 |

Ни один вариант не дал завершённого discovery. Отдельно отмечено: явный `esp_ble_gap_set_pkt_data_len()` систематически совпадает по времени с разрывом — команда не успевает встать на канал.

### 6.3 Устранённые различия с эталоном, не давшие эффекта

| Правка | Основание | Итог |
|---|---|---|
| Свой `Exchange MTU Request` убран | телефон своего не шлёт, только отвечает | без эффекта |
| Пауза 400 мс до discovery | у телефона 0,575 → 0,978 с | без эффекта |
| Интервал 7,5 мс, timeout 5 с | кадр 153 | достигнут (`conn_int = 6`), без эффекта |
| Локальная приватность (RPA) вместо публичного адреса | телефон и Windows ходят с RPA | включилась (`status = 0`), без эффекта |
| Сырое чтение по handle убрано | телефон так не делает | линк живёт дольше (11,5 с против 5), ответа нет |
| Явные preferred conn params убраны вовсе | как у ESPHome с прибором 1.7 | без эффекта |

### 6.4 Гипотезы, снятые измерением

Шифрование · обмен MTU · мощность передатчика · дальность (RSSI −63 дБм, 30 см, одна комната) · неверные handle · параметры соединения вне допустимого диапазона · перезагрузка прибора · конкуренция за прибор со стороны ПК (перепроверено при выключённом Bluetooth на ПК) · PSRAM платы · уровень логирования · WiFi/BLE coexistence как единственная причина.

### 6.5 Два контрольных опыта, снимающие подозрение с нашей стороны

**Вторая физическая плата.** Та же прошивка без единого изменения залита на другой экземпляр ESP32-S3. Поведение идентично: MTU проходит, discovery молчит, разрыв `reason = 8` через 7,3 / 7,7 с. **Железо исключено.**

**Эталонный GATT-сервер.** Ранее работоспособность нашего клиента была допущением — он не прочитал ничего ни с одного устройства за всю серию. Проверено: плата №1 подняла канонический `gatt_server` из ESP-IDF, плата №2 с нашим клиентом (цель переключена макросом) подключилась к ней:

```
I (6589) GATTC evt=7 gattc_if=4   x4      SEARCH_RES — сервисы приходят
I (6599) SEARCH_CMPL status=0 services=4
```

Соединение держалось все 60 с захвата без разрывов. **Клиент, стек, конфигурация и железо исправны.**

## 7. Регрессия 1.7 → 1.8

Единственная связка, где всё работает с ESP32, — прибор с **прошивкой 1.7**:

| | Прибор FW **1.7** | Прибор FW **1.8** |
|---|---|---|
| Шлюз | ESP32-S3, ESPHome | ESP32-S3, та же прошивка шлюза |
| Точка доступа | одна и та же | одна и та же |
| RSSI | −68 дБм | −74 дБм; в контрольном опыте на 30 см — −63 дБм |
| `on_connect` | ✅ срабатывает | ❌ не сработал ни разу |
| Discovery | ✅ завершается | ❌ не завершается никогда |
| Аптайм | **19 ч, 0 реконнектов**, данные текут | разрыв каждые 5–9 с |

Прибор 1.7 работает с тем же кодом шлюза. Сведениями о том, что именно изменилось в BLE-стеке прибора между 1.7 и 1.8, мы не располагаем (со слов изготовителя — «версия BLE изменилась», 1.2 → 1.3).

## 8. Что мы просим у специалиста

Вопросы к изготовителю прибора либо к специалисту по BLE, располагающему сниффером эфира:

1. **При каком условии BLE-стек прибора v1.8 перестаёт обслуживать ATT-запросы, ответив при этом на `Exchange MTU Request`?** Мы наблюдаем ровно это состояние: MTU обменян, discovery игнорируется, затем молчание на канальном уровне.
2. **Есть ли в v1.8 ограничение или белый список по параметрам соединения, DLE, PHY, типу адреса центрального или порядку процедур**, которого не было в v1.7?
3. **Известна ли изготовителю несовместимость v1.8 с центральными на чипах Espressif?** Это массовый класс BLE-шлюзов (Home Assistant, ESPHome, Bluetooth-proxy), и для нашего проекта проблема блокирующая.
4. Если проблема воспроизводится у изготовителя — **возможен ли откат на 1.7 или исправление в следующей версии.**

**Что мы готовы предоставить:** сырой btsnoop рабочей сессии телефона, полные UART-логи всех прогонов обоих стеков, суточный журнал мониторинга с ПК (26 МБ), исходники минимального клиента-воспроизводителя на ESP-IDF (Bluedroid и NimBLE).

**Следующий наш шаг:** снятие собственной трассы Link Layer через `CONFIG_BT_HCI_LOG_DEBUG_EN` (дамп HCI средствами ESP-IDF, без внешнего сниффера) и сравнение с телефонной трассой по тем же полям.

## 9. Как воспроизвести

Минимальный воспроизводитель — клиент на чистом ESP-IDF v5.4, ESP32-S3:

1. `CONFIG_BT_GATTS_ENABLE=y`, зарегистрировать GATTS-приложение с пустым обработчиком (иначе прибор не получит ответа на свой MTU-запрос и дело не дойдёт даже до этой точки).
2. Сканировать по имени `MR107*`, тип адреса цели — **RANDOM**.
3. Подключиться, дождаться `ESP_GATTS_MTU_EVT` (придёт раньше `OPEN_EVT`).
4. Вызвать `esp_ble_gattc_search_service()`.
5. Наблюдать: `SEARCH_RES`/`SEARCH_CMPL` не приходят; через 5–9 с `DISCONNECT reason=8`.

Тот же прибор в тот же момент читается с ПК скриптом на `bleak` без единой ошибки.
